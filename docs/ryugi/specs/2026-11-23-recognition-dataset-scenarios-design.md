> 状态：用户 11-23 批准方向（「测试集以真实场景为入口去校验」「场景清单都没啥问题，继续施工」）。
> 取代 `2026-11-23-recognition-dataset-fields-design.md`（v2，按代码 extract 字段出真值）的真值定义；数据仓库、CI、意见服务、pick 沿用。

## 1. 为什么再改

- v1（整帧逐框）：量通用文字识别，图标和装饰字混在里面。
- v2（按代码字段）：字段清单和真值都来自识别代码，是「先画靶子再射箭」，测出来只能是代码按自己的设想读对没有；104 帧回归帧两种后端都是 100%，
  代码不读的东西永远测不出来。
- v3：**先按真实游玩场景定靶子**（每一屏玩家要知道什么、能点什么，`docs/ocr-dataset/scenarios-draft.json`，只看画面起草、用户审过），
  再照画面标真值，最后用真实系统去读，看读对、读错、还是根本没读。

## 2. 场景定义（机读版）

`tools/ocr_dataset/scenarios.json`：每个场景 = 若干**信息项**（key、中文名、类型、重要度、给标注者看的说明）+ 若干**可点项**（按钮文字）。
类型：`int`、`text`、`enum`（给出取值）、`bool`、`list`（元素是若干子项的对象）。值在画面上看不到时写 `null`。

先做四个场景（用户最在意、测试集里帧最多）：考试中、相談商店、H.I.F 轮间商店、选行动；其余场景按同样格式陆续补。
只有图标、画面上没有文字的信息（货架上饮料是哪瓶、背包颜色……）这一批先不标真值，记 `icon_only`，之后单独做。

## 3. 真值怎么来（照画面，不看系统读数）

1. 两个不同来源的 LLM（Claude、Codex）各自看整帧，按场景的信息项清单输出 JSON（提示词里只有场景定义，**不给系统的读数**）。
2. 逐项比：归一后一致 → agreed；不一致 → disputed，进核对页由用户定。
3. 按钮：LLM 给出画面上有哪些按钮文字；位置用 OCR 检测框按文字模糊匹配找回来（只借位置，不借文字），找不到的进核对页让人点一下。
4. 抽查：每批随机抽 agreed 项给用户核对，准确率 ≥ 98% 才算合格。

## 4. 标注格式（schema 3）

```json
{"schema": 3, "id": "...", "image": "...", "sha256": "...", "source": {...}, "platform": {...},
 "scenario": "exam",
 "truth": {"turns_left": 9, "exam_attr": "vocal", "multiplier_pct": 2805,
           "hand": [{"name": "気まぐれハート", "plus": true, "cost_type": "genki", "cost": 1}, ...]},
 "buttons": [{"label": "SKIP", "box": [560, 760, 640, 820]}],
 "item_status": {"hand[2].cost": "disputed"},
 "answers": {"claude": {...}, "codex": {...}}}
```

## 5. 校验真实系统

- 每个场景写一个**适配器**：把真实系统这一屏的读数（判页 + extract + 整帧文字）换成场景信息项的形状；按钮用系统同样的找法（整帧文字 + 关键词）看能不能找到、位置落不落在按钮框里。
- 每一项三种结果：**读对 / 读错 / 没读**（系统根本不产出这一项 = 覆盖缺口）。
- 换 OCR 后端（Vision / PP-OCRv3 / SIMD）各跑一遍，同一套比。
- 报告：按场景、信息项、重要度出读对率；「没读」单独列（这是 v2 测不出来的）；高重要度项放最前。

## 6. 交付顺序

1. 场景机读定义（四个场景）+ schema 3 校验。
2. 双 LLM 标注 + 比对 + 按钮定位；先跑考试 15 帧看一致率，调提示词。
3. 核对页（逐项）+ 写回；用户核对考试 / 商店 / 选行动三类。
4. 四个场景的适配器 + 校验报告（Vision、PP-OCRv3）。
5. 补采编成菜单、开局流程等缺截图的场景；Windows 上跑 SIMD。
