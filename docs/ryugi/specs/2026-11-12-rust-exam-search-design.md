## 为什么做

- 实战通关比 bench 榜单重要（用户 11-12 方向 1）。DMM 测试局一直是本战第 3：dmmt2 总分 785,187，第 1 名约 108 万。

  （同卡组同种子：R1 318,933 对实际 308,844，R2 312,805 对 347,588）。夺冠要打出上限，单靠一个网络凭直觉出牌不够。

- 用户 11-12 方向 2、3：只留 hiro-gakumas-hero 一个仓库，全部开源，「不读种子」是整个项目的规矩。

## 目标

1. 实战考试（选拔三场 + 本战 R1 / R2）每一步由 Rust 里的 GNRPA 搜索出牌，只用画面可见信息，每步 15 秒（可配）。
2. 培育里的选择评估（技能卡三选一、相談买卡 / 饮料、轮间买饮料 / 回体力 / 刷新）在模拟考试时改用 UINet 续打，替换现在的社区规则续打（替身层）。
3. 规则只在 Rust 里留一份：搜索、续打、世界采样都在 Rust 里闭环跑完，中途不回 Python。

## 不做（这一期）

- 不搬 GKMS 的 C++ 搜索代码：GKMS 没有许可证，搬进来违背「全部开源」。GNRPA 按公开论文在 Rust 里自己写。
- 不读种子、不读存档里的隐藏信息（山札顺序、随机数）。搜索只在随机补全出来的「世界」里进行。
- UINet 不进 Rust：培育评估一次几百局，UINet 留在 Python（onnxruntime）里跑够用；以后要让 UINet 当搜索的续打 / 先验时再搬。
- 培育的非评估决策（选行动、外出等，现在规则 + LLM）不动。
- 不换偶像：只保证 Campus 広（i_card-shro-3-007）。别的偶像要先补「画面读指针」（任务 ① 报告）。

## 反目标（做了就是做错）

- 搜索出错或超时就卡住：任何一步都必须在预算内给出一手，最差退回 UINet，再退回规则。

### 第 1 部分：从画面建搜索起点（最关键）

现在实战唯一的引擎局面来自模拟器跟踪（`hiro.sim.screen_source`），它从 10-19 那局的模板开局再按画面对齐，附魔、P 道具都是那局的。
搜索要的是「这一局」的局面，所以新建一个转换：`UIObs + 本局编成 → gakumas_exam_rs 的局面 JSON`（`io::import` 吃的格式），每步现建，不跟踪。

- 画面可见、UIObs 里有的：回合、剩余回合、每回合属性（已见的照记，未见的按配额；搜索时再按配额随机）、倍率、分数、体力、元気、
  状态（やる気、好印象…）、手牌（含强化）、山札 / 弃牌 / 除外（无序，来自 ScreenTracker；保留区现在恒为空，广的牌组不用）、本回合已出牌数、饮料、附魔。
- 画面看不到的中途计数（**3940a9 的判断：接受近似，不扩记账**）：附魔剩余次数除 P 道具（画面图标有数字）外按初始值；附魔的回合内次数、
  `counters`、本回合已发动的支援、手牌的考试中成长（`grow_after`）按开考时的值。近似会让搜索偶尔把用过的一次性效果当成还能触发；
  先接受，验证 2 量出影响再决定要不要补。
- 画面看不到、要从本局记录来的：
  - **P 道具**：偶像自带的已知；培育里拿到的要记账。选 P 道具页能读到名字（`vision/deck.py` 的 `_pitems_by_name`），
    在 PITEM_ACQUIRE 事件里写进 `produce.items`（这个字段现在从来没填过）。P 道具的触发效果会改变后面的回合，搜索必须有它。
  - **回忆技能、支援卡**：开局编成方案（`brain/formation_plan.py` 写的 `conf/formation-plan.json`）里有。
  - **卡牌定制**：牌组页只读到「有没有定制」，读不到是哪一种。先按这张卡最常见的定制补（同任务 ① 卡组对照的做法），并记一笔。
- 每步建出来以后，和画面再核一遍（**3940a9 的判断**）：核引擎自己算出来、画面上也看得到的东西——合法动作集合、每张手牌能不能打、
  每张卡的费用。对不上就这一步不搜，退回 UINet；一场里连续 3 步对不上，这场剩下的步都退回 UINet，日志写明。
- 编成来源（**3940a9 的判断**）：回忆、支援卡（含租借、等级、凸数）以开局编成方案为准——开局核对（`produce/formation_check.py`）
  已经保证实际编成和方案一致，对不上不开局；支援卡的强化概率等按主数据和等级算。同名 P 道具分不清是哪个时取候选里的第一个并记一笔。
  P 道具的定制（PITEM_CUSTOMIZE）知道就带上，不知道按未定制。

### 第 2 部分：Rust 里的世界采样

在 `gakumas_exam_rs` 加 `sample_world(&Exam, seed) -> Exam`：只重排看不到的部分，保留看得到的。

- 重排：山札顺序（已公开的山札顶几张保留，同 Python 版 `determinize_hidden`）、随机数状态、未见回合的属性（按本场配额）。

### 第 3 部分：Rust 里的 GNRPA

`search(state_json, worlds, seconds, threads, seed) -> (第一手, 各候选的票数 / 平均分)`，Python 一次调用拿结果。

- 每个世界独立跑 GNRPA（嵌套层数、每层迭代数、学习率可配），世界之间并行（线程池），到时间就停。
- 每个世界给出一条最好路线，取它的第一手（跳过选牌类内部动作）投票；平票比平均终局分。
- 续打（GNRPA 的 playout）用带偏置的随机：偏置按 GNRPA 论文的写法用简单特征（动作类型、卡、回合位置…）；具体特征和参数留给实现时
  在 bench 上调。
- 时间到了一个世界都没跑完：返回空，Python 退回 UINet。

### 第 4 部分：接进实战（ExamAdvisor）

- 新的出招插件 `hiro.search.advisor:SearchAdvisor`（名字可改），做缺省；`HIRO_EXAM_SEARCH=0` 回到现在的 bench 中转层（UINet）。
- 每步：建起点（第 1 部分）→ Rust 搜索（15 秒）→ 动作映射回画面槽位（复用 bench_bridge 的映射）→ 点击。
- 退回顺序：建起点失败 / 和画面核不上 / 搜索出错或没结果 → UINet（现有中转层）→ 规则。日志写明每次退回的原因，trace 的决策来源记 `search`。
- 每步记：起点局面摘要、世界数、各候选票数、耗时。复盘页能看到。
- 搜索期间游戏画面不动（考试是回合制，等多久都不影响），但「决策帧过时」检查要放宽到搜索时长以上，免得白搜。

### 第 5 部分：培育评估改用 UINet 续打

- `hiro.sim.policies` 加一个续打策略 `uinet`：每一步把模拟器局面转成 UIObs（`bench_bridge.uiobs.from_engine`，引擎局面在这里是精确的）交给 UINet。
- `hiro.sim.interval.evaluate` 和三选一 / 相談的评估，缺省续打策略从 `expert`（社区规则）换成 `uinet`；`HIRO_PRODUCE_POLICY=expert` 回退。
- 评估是多进程跑的，每个工作进程各自加载一次 UINet 模型（onnxruntime 1.14 + 转换过的模型，已有）。
- 时间：轮间评估现在自适应 16–100 局；换 UINet 后每步多约 10 毫秒，评估时间会变长。实现时先量，必要时把局数上限调低。

### 11-14 查 GKMS 怎么处理对手和名次（只读参考，GKMS 没有许可证，不搬代码）

- 对手：`TowerCatalog.opponents(stage)` 按层的 `produceExamBattleNpcGroupId` 取对手组，每行一个对手：最终分数区间
  （scoreMin / scoreMax）、分段比例（op / mid / ed，分数在考试前中后段怎么分）、三属性比例。对手只参与排名，不影响出牌规则。
  我们的 Rust 引擎已经有 `npc_scores`（「对手各回合分数，名次用，规则不读」），不用新加规则。
- 名次 / 星：★1 = 第 3 名、★2 = 第 2 名、★3 = 第 1 名（8a3a1e7 按 GKMS 10 局实机抓包）。对手实际分数只知道区间，
  保守口径 = 超过 scoreMax 才算赢过他（协调定的排序主依据）。26 / 27 层 ★3 另要通关时条件（低下状態 ≥ 2 / 除外 SSR ≤ 5）。
- 机关：按（机制，层）取机关组（主数据 150 组，80 组有两个变体）。我们的 Rust 引擎已能导入 `gimmick_schedule`。
- 回合数 / 审查基准：在 battle_config 里（id 里带三属性基准和 `turn_N`）；三属性倍率由 8a3a1e7 的 `score_bonus_permils` 算。
