# OCR 测试集与贡献规范：设计稿（2026-11-23，待批准）

设计讨论（两轮问答）的结论。标「我定的」的是实现者代为做的决定，其余是你定的或接受了推荐。

## 1. 为什么做

Windows / DMM 上的文字识别（RapidOCR + PaddleOCR PP-OCRv3 日文模型）经常认错形近字（「編」认成「綿」等），已经多次导致判页、读数出错。
你在 DMM 540×960 窗口上测，字本身完全看得清，问题在 OCR。试过 PP-OCRv5 和 Windows 自带 OCR，都不如现在的 v3；开着的 PR #9
（SIMD PaddleOCR 后端）在 33 张模板图上 33/33，但没在 DMM 实机帧上测过。

现在没有任何一个数能说明 OCR 到底错多少、错在哪类场景：

- 现有的 DMM 回归集（`tests/dmm_regression.json` + 104 帧）测的是页面判定和最终读数，**明确不比 OCR 原文**；
- 11-06 的端到端回归（RapidOCR 897 个用例 77 个失败）是按用例算的，截图主要来自 Mac / MuMu，分辨率比 DMM 540 高；
- 识别层的黄金数据全是 Apple Vision 的结果。

这套测试集要补上这一层：**每段文字应该读成什么**，按场景出字错率，能对比不同 OCR 后端；同时定一套规范，让其他开发者从自己的机器
（不同平台、分辨率）贡献样本。

## 2. 目标、不做的、坚决不做

| 类别 | 内容 |
|---|---|
| 目标 | 一套 OCR 测试集：整帧截图 + 每个文字框的位置和正确文字 + 场景标签，分「核心集」（覆盖各场景）和「进阶集」（失败率高的场景专门加量）。 |
| 目标 | 一个评测命令：对一个或多个 OCR 后端出字错率、整行全对率、关键词命中率、耗时，按标签分组，能两两对比。 |
| 目标 | 一套贡献规范 + 投稿命令：其他开发者从自己的 trace 里挑帧打包、提 PR；标注在合入时由 AI 流程完成，投稿的人不用标。 |
| 目标 | 第一份报告回答：在 DMM 540 上，现在的 PP-OCRv3、PR #9 的 SIMD 后端、PP-OCRv3 加「限定字符范围」三种谁的字错率最低。 |
| 不做 | 页面判定 / 字段读数的回归（现有 `dmm_regression` 继续负责）；训练或微调模型（测试集以后可以给它用，这次不做）；Go 版的评测工具（Go 迁移暂停中）。 |
| 坚决不做 | 截图进主仓库（仓库规矩）；把截图发到第三方 OCR 云服务（标注用的 LLM 是项目已有的 claude / codex 调用，同样的数据流）。 |

## 3. 已定

- 数据单位：**整帧截图 + 标注数据**（每个文字框的位置、正确文字、标签），图片本身不动，换预处理 / 检测模型时能从原图重新评测（你定的）
- 框不由人画：用 OCR 的文字检测自动生成（接受推荐）
- 图片放单独的私有仓库，贡献者提 PR；主仓库只放规范、标注格式、工具（你定的）
- 私有仓库：GitHub `matto49/hiro-ocr-dataset`，图片用 Git LFS（接受推荐）
- 正确文字由 AI 识别匹配得出：每个框取 Apple Vision、LLM 看图、游戏词表吸附三方答案，一致就自动入库，有分歧的进「待定」清单偶尔人看一眼（你定的方向 + 接受推荐的做法）
- 标签贴合系统已有的信息：页面名用判页结果，平台 / 分辨率 / 设备用运行元信息，文字类型按这个框被哪个识别字段用到（接受推荐）
- 投稿：仓库里一个命令从 trace 自动挑帧、去重、打包，放进数据仓库的投稿目录提 PR（接受推荐）
- 评测输出：字错率、整行全对率、关键词命中率、单帧耗时，按标签分组、能对比后端（你同意）
- 不遮挡截图：只有用户等级信息，私有仓库（你定的）
- 第一批样本：现有 104 张 DMM 帧 + Windows worktree 里的 DMM trace（优先）+ 主仓库 `tests/fixtures` 的 Mac 帧当对照；**量太大，先分类精筛，重点覆盖各个场景；失败率高的场景另做进阶集**（你定的）
- 第一个要回答的问题：见第 2 节最后一条目标（接受推荐）
- 工具用 Python 写，放主仓库（我定的：Go 迁移暂停到 Python 版稳定后；要比的后端里 PR #9、winocr 只有 Python 接口）

## 4. 现状里要注意的两件事（读代码发现的）

1. **trace 里的帧已经缩放过**：`feat_matto_oss_windows/traces` 126 次运行、3.4 万帧，存的都是缩放到 720×1280 的 JPEG（质量 85），
   DMM 原生的 540×960 没留下来。这和 OCR 现在实际吃进去的图一致（截图先拉到 720 逻辑分辨率再识别），所以**用来评测当前流程是对的**；
   但要量「去掉二次插值」这类改动，需要原生分辨率的帧 → 见 6.6。
2. **trace 没记设备和分辨率**：`run.json` 只有开始时间，步骤备注里也没有。老 trace 的平台标签只能靠一张「运行名 → 平台」对照表补
   （见 9.1）；新运行要把设备信息写进 `run.json`（见 6.6）。

## 5. 数据仓库 `hiro-ocr-dataset` 的结构

```
hiro-ocr-dataset/
  README.md / CONTRIBUTING.md   # 贡献规范（第 7 节的内容）
  schema/frame.schema.json      # 标注格式的 JSON Schema，CI 校验
  core/                         # 核心集：精筛后覆盖各场景
    <frame_id>.png|jpg
    <frame_id>.json             # 这一帧的元信息 + 标注
  hard/                         # 进阶集：失败率高的场景专门加量，格式同 core
  inbox/<贡献者>/<日期>/         # 投稿区：图片 + meta.json，还没标注
  disputed.json                 # 待定清单：三方答案不一致的框
  lexicon/                      # 词表快照（生成的，带主数据版本）
  reports/<日期>-<说明>.md|json # 评测报告存档
```

`frame_id` = `<平台>-<来源运行>-<seq>`（例如 `dmm540-maindmm1m-20261110-205150-00051`），同一帧只收一次（按内容哈希去重）。

### 5.1 一帧的标注文件

```json
{
  "schema": 1,
  "id": "dmm540-maindmm1m-20261110-205150-00051",
  "image": "dmm540-maindmm1m-20261110-205150-00051.jpg",
  "sha256": "…",
  "source": {"run": "maindmm1m-20261110-205150", "seq": 51, "contributor": "matto", "captured": "2026-11-10"},
  "platform": {"kind": "dmm", "native": [540, 960], "stored": [720, 1280], "device": "windows_background", "note": "公司 1080P 显示器"},
  "page": "ACTION_SELECT",
  "boxes": [
    {"id": 0, "box": [312, 1140, 408, 1176], "text": "編成",
     "status": "agreed",
     "answers": {"vision": "編成", "llm": "編成", "lexicon": "編成", "rapidocr": "綿成"},
     "tags": {"field": "action_select.button", "type": "button"},
     "ignore": false}
  ]
}
```

- `box`：整帧坐标 (x1, y1, x2, y2)，按 `stored` 尺寸。
- `status`：`agreed`（三方一致，自动入库）/ `resolved`（有分歧，人定的）/ `disputed`（待定，评测时不计分）/ `ignored`（不评测：装饰字、读不出的艺术字、动画模糊帧）。
- `answers`：留下各方原始答案，以后复查标注质量、看某个后端的错法用。`rapidocr` 等被评测后端的答案只记录、不参与定正确文字。
- `tags.type`：`button` / `title`（弹窗标题、页头）/ `name`（卡名、饮料名、P 道具名、偶像名）/ `number`（分数、P 点、体力、回合）/ `body`（说明文、效果文）/ `label`（角标、小字标签）/ `other`。
- `tags.field`：这个框被哪个识别字段读（例如 `consult.shelf.name`），对不上为 `null`。

## 6. 工具（主仓库 `tools/ocr_dataset/`）

全部是 `python -m tools.ocr_dataset <子命令>`，数据仓库位置由 `HIRO_OCR_DATASET`（缺省 `../hiro-ocr-dataset`）指定。

### 6.1 `pick`：从 trace 里挑帧（精筛）

1. 读一批 trace 目录，每帧取页面名（trace 里记的判页结果，没有就现跑判页）、平台（见 9.1 的对照表 / `run.json`）。
2. 去重：同一运行里缩略图差小于阈值的连续帧只留一张（复用 `repeat_guard` 的 90×160 灰度缩略图与 `SCREEN_DIFF`）；跨运行按内容哈希去重。
3. 分层抽样：按「平台 × 页面」分格，每格最多 N 张（我定的：N = 3，DMM 540 的格放宽到 5）；再检查各文字类型（5.1 的 `type`）
   至少有 K 个框（我定的：K = 30），不够的从剩下的帧里按类型补。
4. 输出到 `inbox/<贡献者>/<日期>/`：图片原样拷贝 + `meta.json`（每帧的来源、平台、页面，以及投稿人可选的「这帧哪里认错了」说明）。

目标规模（我定的）：核心集 200–400 帧，其中 DMM 540 不少于一半。

### 6.2 `label`：AI 标注（合入投稿时跑，或者维护者本地跑）

1. **出框**：Apple Vision 和 RapidOCR 各做一次整帧检测，按 IoU 合并（同一段字取并集框）；整帧放大倍数同 `hiro.vision.ocr.SCREEN_SCALE`。
   只能在 Mac 上跑（要 Vision）。
2. **三方答案**（每个框）：
   - `vision`：Apple Vision 在这个框的裁图上识别（放大 3 倍双三次，同现有 `hiro.vision.ocr` 的 Vision 调法）；
   - `llm`：LLM 看图给出文字；走项目已有的 `hiro.brain.llm` 适配器（`HIRO_LLM`），提示词要求「只抄写看到的字，不纠正、不补全」。
     **每帧问一次**（我定的）：整帧图上标出编号框，回复按编号给每个框的文字；一批 300 帧约 300 次调用，不是每框一次；
   - `lexicon`：把前两方的答案在游戏词表里就近吸附（编辑距离，按词长限定容错，规则同 PR #21 的 textnorm 容错匹配）；吸附不到为空。
3. **定正确文字**：三方归一（NFKC、去空格、全半角统一）后一致 → `agreed`；`vision` 与 `llm` 一致而词表没有这个词 → 也算 `agreed`
   （词表不全不该拦住）；其余 → `disputed`，写进 `disputed.json`。
   真正独立的只有 `vision` 和 `llm` 两方，`lexicon` 是它们的吸附结果，只用来在两方不一致时帮着挑；所以 `vision ≠ llm` 时，
   只有其中一方恰好吸附到词表、另一方吸附后也落到同一个词，才算 `agreed`，否则一律 `disputed`（我定的）。
4. **标注质量把关**（我定的）：每批从 `agreed` 里随机抽 50 个框，生成一页给人核对，准确率 ≥ 98% 这批才算标注合格；不到就看错在哪、调规则重跑。
   形近字恰好是两方最容易不一致的地方，所以待定框不能悄悄丢掉：**待定框占比 > 5% 时不出正式报告**，先在 `review` 页清到 5% 以下；
   报告里始终写出待定占比，并单独列「待定框里各后端的读法」，避免难样本被系统性剔除、字错率显得偏低。
5. **标签**：`page` 取帧里的判页结果；`tags.field / type` 按 6.3 的映射；对不上的 `type` 用简单规则兜底（只有数字 → `number`；
   在弹窗标题条 y 范围里 → `title`；其余 `other`）。

### 6.3 文字类型映射（`tags.field`）

识别代码里每个页面读哪些区域（`hiro.vision` 各页的 ROI / 锚点）整理成一张「页面 → [(字段名, 区域, 类型)]」的表，框的中心落在哪个区域就标哪个字段。
这张表放在 `tools/ocr_dataset/fields.py`，先覆盖核心集里出现的页面；没覆盖到的页面所有框 `field = null`、`type` 走兜底规则。

### 6.4 `review`：人看待定框

生成一个本地 HTML 页（不发布到任何在线平台）：每个待定框显示裁图、各方答案，点一个答案或手填，保存回 `<frame_id>.json`（`status = resolved`）。
也可以把整个框标成 `ignored`。

### 6.5 `eval`：评测

```
python -m tools.ocr_dataset eval --backend rapidocr,simd,rapidocr+charset --set core [--tags platform=dmm540] [--compare reports/xxx.json]
```

- **后端**：用 `hiro.vision.ocr` 的整帧接口（`screen_texts`）跑，和实机流程同一条路；一个后端 = 一个 `HIRO_OCR` 取值，外加实验后端
  （`rapidocr+charset`：PP-OCRv3 在 CTC 解码前把游戏字表以外的字屏蔽掉，只在评测工具里实现，不改实机代码）。
  字表（我定的）：KAA 主数据**所有文字字段**（名字和说明文、效果文都算，正文里的汉字才覆盖得到）里出现过的字 + 识别代码里的界面文字常量
  + 全部平假名 / 片假名 + 半角 / 全角数字和英文字母 + 常用标点（％、＋、×、・、〜、「」、（）等）。**只从主数据和代码来，不从标注文字来**（否则评测泄题）。
- **框对齐**：识别出的框和标注框按 IoU ≥ 0.5（或中心落在框内）配对；标注框没配上 = 整段漏读（字全算错）；多出来的框单独计数，不算进字错率。
- **指标**：
  - 字错率 CER = 编辑距离之和 / 正确文字总字数（文字先 NFKC、去空格）；
  - 整行全对率；
  - 关键词命中率：正确文字里出现的游戏词表词，在识别结果里完整出现的比例（最接近「会不会导致点错 / 读错」）；
  - 单帧耗时（P50 / P90，不含首次加载）；
  - 漏读率、多读框数。
- **分组**：按平台、页面、文字类型出表；`disputed` / `ignored` 的框不计分。
- **输出**：markdown 表 + JSON（可以作为下一次 `--compare` 的基线）；`--compare` 时每格给出增减。
- **错例清单**：每个后端字错率最高的 50 个框（裁图路径 + 正确文字 + 读成什么），方便人看错法。

### 6.6 新运行补元信息（主仓库，小改动）

- `run.json` 加 `platform`：设备种类（`HIRO_DEVICE` / 实际驱动）、游戏客户区原生尺寸、截图方式、OCR 后端。缺省开（只多写几个字段，不改行为）。
- 可选开关 `HIRO_TRACE_NATIVE=1`（缺省关）：存帧时另存一张原生分辨率的 PNG（`frames/<seq>.native.png`），以后用来评测预处理改动。
  磁盘占用大，只在采集测试集时开。

### 6.7 进阶集（`hard/`）

- 来源：核心集评测里字错率高的场景（某个「平台 × 页面 × 类型」格的 CER 明显高于平均，阈值实现时按第一份报告定），以及投稿里带「这里认错了」说明的帧。
- 做法：对这些场景再从 trace 里按 6.1 的流程多挑（每格不设上限，只去重），同样走 `label`。
- 评测时 `--set hard` 单独出表，不和核心集混算。

## 7. 贡献规范（写进数据仓库的 CONTRIBUTING.md）

1. 用自己的运行（建议开 `HIRO_TRACE_NATIVE=1`）攒 trace；要投的运行最好跑过多种页面。
2. `python -m tools.ocr_dataset pick <trace 目录…> --contributor <名字>`：自动挑帧、去重、打包到 `inbox/`。可以加 `--note <seq>=<说明>`
   标出「这帧哪里认错了」。
3. 在数据仓库开分支、提 PR。PR 里写平台、窗口大小、设备、OCR 后端（`run.json` 有的话自动带上）。
4. 维护者合入前跑 `label`：标注由 AI 流程完成，投稿人不用标；待定框维护者在 `review` 页处理或标 `ignored`。
5. CI 校验：JSON Schema、图片和标注一一对应、`sha256` 对得上、`frame_id` 不重复。
6. 不收：横屏 LIVE 演出帧、全黑 / 加载中的帧、和已有帧内容哈希相同的帧。

## 8. 交付顺序

1. 数据仓库骨架（目录、schema、CONTRIBUTING、CI 校验）。
2. `pick` + 第一批精筛（104 张 DMM 帧 + Windows DMM trace（Mac 上的 `feat_matto_oss_windows/traces` 和 Windows 上 `hiro-w4` 的 traces）+ Mac 对照）。
3. `label`（三方答案 + 词表吸附）+ `review` 页；跑完第一批，处理待定框。
4. `eval`（含 `rapidocr+charset` 实验后端）+ 第一份报告：PP-OCRv3 / PR #9 SIMD / PP-OCRv3 + 字表，按场景出表。
5. 主仓库 `run.json` 补元信息 + `HIRO_TRACE_NATIVE` 开关。
6. 按第一份报告挑出高失败场景，做进阶集。
